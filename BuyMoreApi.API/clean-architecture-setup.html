Prerequisites & Folder Layout

Tools

Before you start

Make sure the .NET SDK and VS Code are ready. These steps assume .NET 8 or 10, PowerShell, and the C# extension in VS Code.
SDKdotnet --version ≥ 8.0.0
EditorsVS Code + C# Dev Kit
DatabasePostgreSQL (or preferred provider)
Solution layout target
  • src/BuyMoreApi.API — ASP.NET Core host (controllers, middleware).
  • src/BuyMoreApi.Application — DTOs, abstractions, validators.
  • src/BuyMoreApi.Domain — Entities, enums, constants.
  • src/BuyMoreApi.Infrastructure — EF Core, repository implementations, service adapters.
Why this shape? Presentation depends on Application contracts only. Infrastructure depends on both Domain and Application, providing actual implementations without leaking vendor specifics.

Bootstrap the Solution

CLI

Create solution + projects

  1. Create the root directory and solution:
    CLISolution scaffolding
    mkdir Coh2/BoomerApi
cd Coh2/BoomerApi
dotnet new sln -n BuyMoreApi
  2. Scaffold the four primary projects:
    CLIProject creation
    dotnet new webapi   -n BuyMoreApi.API           -o src/BuyMoreApi.API
dotnet new classlib -n BuyMoreApi.Application   -o src/BuyMoreApi.Application
dotnet new classlib -n BuyMoreApi.Domain        -o src/BuyMoreApi.Domain
dotnet new classlib -n BuyMoreApi.Infrastructure -o src/BuyMoreApi.Infrastructure
  3. Add every project to the solution (so VS Code and CLI tooling see them):
    CLIdotnet sln add
    dotnet sln BuyMoreApi.sln add src/BuyMoreApi.API/BuyMoreApi.API.csproj
dotnet sln BuyMoreApi.sln add src/BuyMoreApi.Application/BuyMoreApi.Application.csproj
dotnet sln BuyMoreApi.sln add src/BuyMoreApi.Domain/BuyMoreApi.Domain.csproj
dotnet sln BuyMoreApi.sln add src/BuyMoreApi.Infrastructure/BuyMoreApi.Infrastructure.csproj

Wire Project References

References

Respect the dependency rule

Clean architecture dictates reference direction: API → Application, Infrastructure → Application & Domain, Application → Domain.
CLIdotnet add reference

dotnet add src/BuyMoreApi.Application/BuyMoreApi.Application.csproj reference src/BuyMoreApi.Domain/BuyMoreApi.Domain.csproj
dotnet add src/BuyMoreApi.Infrastructure/BuyMoreApi.Infrastructure.csproj reference src/BuyMoreApi.Application/BuyMoreApi.Application.csproj

Model the Domain

Domain

Entities, Enums, Value Objects

Domain project should stay persistence-agnostic. Typical content:

  • Entities/User.cs, Entities/Order.cs etc. containing only business properties and behaviors.
  • Enums/Role.cs for strongly-typed enums.
  • Constants/RoleNames.cs for re-usable string constants (guarding policies).
  • ValueObjects (e.g., Email) when richer types are needed.
C#Entity example
namespace BuyMoreApi.Domain.Entities;

public class Order
{
    public Guid Id { get; set; }
    public Guid UserId { get; set; }
    public decimal TotalAmount { get; set; }
    public DateTime CreatedUtc { get; set; }

    public void UpdateTotal(IEnumerable<OrderLine> lines)
        => TotalAmount = lines.Sum(l => l.Quantity * l.UnitPrice);
}
No EF references hereKeep data annotations out of the Domain layer; configure persistence in Infrastructure.

Build the Application Layer

Application

Contracts, DTOs, Validation

  • DTOs: e.g., RegisterRequest, LoginResponse.
  • Interfaces: service abstractions (IUserService, IPaymentService, IFileStorage).
  • Options: JwtSettings, MonitoringOptions, MailOptions.
  • Validation: FluentValidation classes per request DTO.
  • Utilities: password hashing helpers in a static utility class.
RegistrationExpose an extension method (e.g., services.AddApplicationValidation()) that scans for validators via AssemblyScanner.

Implement Infrastructure

EF Core

Persistence + external services

Key folders
  • Persistence/AppDbContext.cs (inherits DbContext).
  • Persistence/Configurations for IEntityTypeConfiguration classes.
  • Persistence/Repositories implementing interfaces defined in Application.
  • Extensions/ServiceCollectionExtension.cs to register all dependencies in one spot.
  • Monitoring/, Notifications/, Payments/, Storage/ folders for adapter implementations.
Service registration
C#AddDependencyInjection excerpt
public static class ServiceCollectionExtension
{
    public static IServiceCollection AddDependencyInjection(this IServiceCollection services, IConfiguration configuration)
    {
        services.Configure<JwtSettings>(configuration.GetSection("JwtSettings"));
        services.Configure<MonitoringOptions>(configuration.GetSection("Monitoring"));
        services.Configure<FileStorageOptions>(configuration.GetSection("FileStorage"));

        services.AddSingleton<IMetricsService, MetricsService>();
        services.AddScoped<IMailService, SmtpMailService>();
        services.AddHttpClient<IPaymentService, PaystackPaymentService>();
        services.AddScoped<IPaystackWebhookService, PaystackWebhookService>();

        services.AddScoped<LocalFileStorage>();
        services.AddScoped<AwsS3FileStorage>();
        services.AddScoped<AzureBlobFileStorage>();
        services.AddSingleton<FileStorageFactory>();
        services.AddScoped<IFileStorage>(sp => sp.GetRequiredService<FileStorageFactory>().Create());
        // ... repositories, user service registrations ...
        return services;
    }
}

AppDbContext & EntityTypeConfiguration

EF Core

Keeping EF details out of the Domain

DbContext
C#AppDbContext skeleton
public class AppDbContext : DbContext
{
    public AppDbContext(DbContextOptions<AppDbContext> options) : base(options) { }

    public DbSet<User> Users => Set<User>();
    public DbSet<Order> Orders => Set<Order>();

    protected override void OnModelCreating(ModelBuilder modelBuilder)
    {
        modelBuilder.ApplyConfigurationsFromAssembly(typeof(AppDbContext).Assembly);
        base.OnModelCreating(modelBuilder);
    }
}
EntityTypeConfiguration
C#Users configuration
public class UserConfiguration : IEntityTypeConfiguration<User>
{
    public void Configure(EntityTypeBuilder<User> builder)
    {
        builder.ToTable("Users");
        builder.HasKey(u => u.Id);

        builder.Property(u => u.Email)
               .IsRequired()
               .HasMaxLength(150);

        builder.Property(u => u.Role)
               .HasConversion()
               .HasMaxLength(40);

        builder.HasMany(u => u.Orders)
               .WithOne()
               .HasForeignKey(o => o.UserId);
    }
}

Configure the Web API Host

Host

Program.cs essentials

Key registrations
  • builder.Services.AddDatabase(configuration); — extension in Infrastructure configuring EF Core + connection string.
  • builder.Services.AddDependencyInjection(configuration); — registers repositories/adapters.
  • JWT authentication configured from JwtSettings.
  • Swagger security definition + requirement (fixing earlier 500 error).
  • Middleware pipeline: HTTPS redirection, global exception handler, request logging, CORS, auth.
Health checksAdding builder.Services.AddHealthChecks() and app.MapHealthChecks("/health") gives ops teams a quick sanity probe.

Standard Practices & Extras

Best Practices

Keep your architecture healthy

  • Environment-specific config: maintain appsettings.{Environment}.json plus dotnet user-secrets for local secrets.
  • Use extension classes (AddApplicationValidation, AddDependencyInjection) to keep Program.cs clean.
  • Avoid static helpers for I/O-intensive work; prefer DI-friendly services to enable testing.
  • Handle external failures: wrap Paystack/S3 calls with retries + logging (Polly).
  • Testing: create xUnit projects referencing Application & Infrastructure; use in-memory providers for EF where acceptable.
  • Observability: standardize on structured logging (JSON) and feed metrics to a dashboard beyond the in-memory buffer when you reach production.
Migrations policyGenerate migrations from the Infrastructure project only; target database should be configured in appsettings.Development.json.
