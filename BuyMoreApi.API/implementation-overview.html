Request Monitoring & Logging

Tracing

Capturing request telemetry without breaking clean architecture

Application Layer
  • MonitoringOptions stores feature toggles (enable/disable, request body capture, ring-buffer size).
  • RequestMetric is a minimal telemetry record (route, status code, duration, timestamp).
  • IMetricsService abstracts metric collection so any host (web, background job, gRPC) can reuse it.
Infrastructure Layer
  • MetricsService keeps a concurrent queue bounded by configuration, enabling cheap in-memory dashboards.
  • Registration happens in ServiceCollectionExtension.AddDependencyInjection, exposing the service as a singleton.
API Layer
  • RequestLoggingMiddleware wraps every HTTP request, optionally buffers payloads, and pushes metrics before logging structured messages.
  • MonitoringController exposes GET /api/monitoring/metrics so the team can inspect the buffered telemetry while developing.
C#Request logging middleware snapshot
public sealed class RequestLoggingMiddleware
{
    public async Task InvokeAsync(HttpContext context)
    {
        var sw = Stopwatch.StartNew();
        string? body = null;
        if (_options.CaptureRequestBody && context.Request.Body.CanSeek)
        {
            context.Request.EnableBuffering();
            using var reader = new StreamReader(context.Request.Body, Encoding.UTF8, leaveOpen: true);
            body = await reader.ReadToEndAsync();
            context.Request.Body.Position = 0;
        }

        await _next(context);
        sw.Stop();

        _metrics.TrackRequest($"{context.Request.Method} {context.Request.Path}", sw.Elapsed.TotalMilliseconds, context.Response.StatusCode);
        _logger.LogInformation("Request {Route} -> {Status} in {Elapsed} ms {Payload}", ...);
    }
}
Why this design?The middleware depends only on IMetricsService, keeping ASP.NET Core aware code inside the API project while still allowing reuse in other hosts.

Mail & Notification Services

Messaging

SMTP + notification fan-out

Contracts & Options
  • MailRequest encapsulates a transactional email (subject, HTML flag, reply-to, attachments).
  • MailOptions stores SMTP host/port/credentials and default sender identity.
  • NotificationOptions toggles delivery channels (email, logging) so environments can opt out.
  • IMailService & INotificationService keep controllers/services decoupled from a specific provider.
Infrastructure Binding
  • SmtpMailService uses SmtpClient under the hood. Attachments are streamed via MemoryStream to avoid locking the original payload array.
  • NotificationService composes IMailService with logging so other transports (SMS, push) can be added without touching consumers.
Credential hygieneAll secrets remain in configuration; the SMTP client never hard-codes passwords and supports SSL/TLS through EnableSsl.

Paystack Payments

Payments

REST integration for transaction init & verification

Application Contracts
  • PaystackOptions (base URL + secret/public keys).
  • PaystackInitializeRequest / PaystackInitializeResponse mirror Paystack’s REST payloads.
  • PaystackVerifyResponse captures the minimal verification data needed by the app.
  • IPaymentService orchestrates interactions without leaking Paystack-specific details to the domain.
Infrastructure Client
  • PaystackPaymentService is registered via AddHttpClient, ensuring resilient HTTP usage (pooled handlers, lifetime mgmt).
  • Requests serialize using System.Text.Json and include the secret key in the Authorization header.
  • Responses wrap Paystack’s usual envelope (status/message/data).
C#Initializing a transaction
public async Task<PaystackInitializeResponse> InitializeTransactionAsync(PaystackInitializeRequest request, CancellationToken ct)
{
    var json = JsonSerializer.Serialize(request, _serializerOptions);
    using var content = new StringContent(json, Encoding.UTF8, "application/json");

    using var response = await _httpClient.PostAsync("/transaction/initialize", content, ct);
    await EnsureSuccessAsync(response);
    return (await DeserializeAsync<Envelope<PaystackInitializeResponse>>(response, ct)).Data;
}
Why HttpClient factory?It avoids socket exhaustion under load and lets us plug Polly policies later without touching the service implementation.

Paystack Webhook Flow

Webhooks

Signature validation & notification hook

End-to-End Path
  1. POST /api/payments/paystack/webhook accepts webhook calls (anonymous allowed).
  2. The controller buffers the raw request body for signature verification.
  3. IPaystackWebhookService verifies the x-paystack-signature header using HMAC-SHA512 and the configured secret key.
  4. After validation, the payload is logged and routed through INotificationService so operators get visibility (currently via email/log; richer integrations can plug in later).
C#Webhook verification snippet
private bool IsSignatureValid(string signature, string rawBody)
{
    using var hmac = new HMACSHA512(Encoding.UTF8.GetBytes(_options.SecretKey));
    var expected = BitConverter.ToString(hmac.ComputeHash(Encoding.UTF8.GetBytes(rawBody)))
                      .Replace("-", "").ToLowerInvariant();
    return string.Equals(expected, signature, StringComparison.OrdinalIgnoreCase);
}
Failure modesIf the signature is missing/invalid or JSON parsing fails, the service throws InvalidOperationException. The controller should translate that into 400 responses; add custom exception handling if you prefer structured error payloads.

Pluggable File Storage

Storage

Local disk, AWS S3, Azure Blob — pick at runtime

Interfaces & Options
  • IFileStorage defines three basic operations: SaveAsync, GetAsync, DeleteAsync.
  • FileStorageOptions carries the selected provider and provider-specific options (local path, AWS credentials, Azure connection string).
Provider Implementations
  • LocalFileStorage writes to the server’s filesystem, auto-renaming files when overwriting is disabled.
  • AwsS3FileStorage streams to S3 using the AWS SDK, handling NotFound gracefully.
  • AzureBlobFileStorage talks to Azure Blob Storage, creating the container on startup if missing.
Factory Pattern

FileStorageFactory inspects FileStorageOptions.Provider and resolves the right implementation from the DI container. The API only depends on IFileStorage, keeping storage decisions in configuration.

Swapping providersFlip FileStorage:Provider in appsettings (values: Local, AwsS3, AzureBlob) and restart; no code changes required.

API Surface & Middleware

Controllers

Endpoints added or modified

New Controllers
  • MonitoringController exposes the metrics buffer.
  • FilesController offers upload/download/delete endpoints secured by [Authorize].
  • PaymentsController now supports initialization, verification, and webhook handling in one place.
Program.cs Adjustments
  • Added console/debug logging providers and HealthChecks.
  • Registered the middleware pipeline (UseMiddleware<RequestLoggingMiddleware>, UseExceptionHandling).
  • Updated Swagger security requirement to use the official OpenApiSecurityScheme/OpenApiReference API.
Swagger repairThe previous security requirement used a helper type that doesn’t exist in the new Swashbuckle version, causing a 500 when loading /swagger/v1/swagger.json. The fix uses OpenApiSecurityScheme and OpenApiReference, restoring compatibility.

Configuration & Secrets

Config

New sections in appsettings.json

  1. Monitoring: toggle capture, request body sampling, and in-memory buffer size.
  2. Mail / Notification: SMTP host, port, credentials, and whether email/log channels are enabled.
  3. Paystack: secret/public keys and base API URL.
  4. FileStorage: provider selection plus provider-specific options.
RememberReplace placeholder secrets before deploying. Consider dotnet user-secrets for local development or Azure Key Vault in production.
